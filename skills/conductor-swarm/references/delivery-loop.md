# Shared swarm delivery loop

Conductor owns the active work graph and integration. Pickup supplies bounded recovery. Cross-Tool Continuity handles an actual session/provider boundary. Domain skills own concrete artifacts. StatusGlance observes activity and acceptance; it does not schedule execution. Operations Pulse handles separately requested recurrence. Skill Feedback Engine handles opted-in improvement proposals.

Observe only relevant changes; shape coherent work packages; run the independent ready set in parallel when supported and authorized; verify continuously and integrate at meaningful milestones; adapt from evidence; continue required in-scope follow-ons or finish the accepted objective. These functions overlap rather than forming a six-agent pipeline.

## Recovery and routing

Consume one recovery receipt with project/objective identity, source revision or fingerprints, verified/claimed/unknown facts, ready work, blocking discrepancies, and next milestone. Recheck consequential changed inputs. Do not repeat Pickup inside Conductor after Pickup already supplied that receipt, or invoke a second Conductor from a continuity adapter.

Reuse the current capability map. Read selected instructions fully, but refresh selection only for a material task/capability change or failed routing. Keep standalone use possible; an absent sibling skill is not a reason to install a whole platform before doing useful work.

## Tandem execution and convergence

Assign a compact brief per coherent outcome: exact scope, ownership, dependency/interface contract, applicable evidence, acceptance criteria, required checks, and expected output. Preserve concurrent changes. One integrator is not one writer for the entire project. Isolate shared resources or coordinate only the conflicting operation.

Run focused checks during implementation. Review a completed lane while independent work continues. Regroup at the agreed integrated milestone. Separate implemented, tested, integrated, and accepted; an agent report is not acceptance evidence.

At a repeated failure, compare the unresolved criterion and new evidence with the previous attempt. If neither changed, change the hypothesis, task boundary, test, contract, or available capability. Do not blindly retry, suppress valid findings, or freeze unrelated lanes. Re-review the changed and affected behavior; expand scope when the evidence identifies broader impact.

## Follow-ons, status, and stopping

Action the next required, ready item within existing authority. Record owner when known and next action for a real gap. Ask only when a missing decision or authority materially changes the outcome. A deferred required gap is not accepted; optional improvements need not keep a completed goal alive.

Use the existing checkpoint as the continuity source. Emit small state changes at task/milestone boundaries, not full dashboards after each command. Status queries read one bounded, correctly identified snapshot. Missing evidence or a missing denominator stays unknown; elapsed time and tool calls do not establish completion percentages.

Finish when the requested outcome is accepted or no authorized useful path remains. Preserve evidence and exact next action. Do not create an unrequested scheduler, publish, switch providers, rewrite skills, or update global memory because a loop ended.

When another process skill prescribes conflicting scheduling, resolve it through the runtime instruction hierarchy and the user's selected workflow. Use compatible bounded testing/review capabilities rather than silently running competing controllers. Project-specific correctness and authority requirements remain intact.
